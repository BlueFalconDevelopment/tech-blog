Bash

Shebang & Script Basics
▸#!/usr/bin/env bash — portable shebang line
▸chmod +x script.sh && ./script.sh — make executable and run
▸set -euo pipefail — exit on error, unset var, or failed pipe stage (put near top of every script)
▸set -x — print each command before running it (debugging)
Variables
▸name="value" — no spaces around =
▸echo "$name" — always quote variable expansions
▸readonly PI=3.14 — constant
▸unset name — remove a variable
▸local x=1 — inside a function, scope to that function
▸${var:-default} — use default if var unset/empty
▸${var:=default} — same, and assigns default to var
▸${var:?error message} — exit with error if var unset
▸${#var} — length of string
▸${var#prefix} / ${var##prefix} — strip shortest/longest matching prefix
▸${var%suffix} / ${var%%suffix} — strip shortest/longest matching suffix
▸${var/old/new} — replace first match
▸${var//old/new} — replace all matches
Arrays
▸arr=(a b c)
▸echo "${arr[0]}" — first element
▸echo "${arr[@]}" — all elements
▸echo "${#arr[@]}" — array length
▸arr+=(d) — append
▸for item in "${arr[@]}"; do ...; done
Conditionals
▸if [[ condition ]]; then ... elif ...; else ...; fi
▸[[ -f file ]] — file exists and is regular file
▸[[ -d dir ]] — directory exists
▸[[ -z "$s" ]] — string is empty
▸[[ -n "$s" ]] — string is non-empty
▸[[ "$a" == "$b" ]] — string equality (use [[ ]], not [ ], for pattern/regex support)
▸[[ "$a" =~ regex ]] — regex match
▸(( a > b )) — arithmetic comparison
▸case "$var" in pattern1) ... ;; pattern2) ... ;; *) ... ;; esac
Loops
▸for i in {1..10}; do ...; done
▸for f in *.txt; do ...; done
▸while read -r line; do ...; done < file.txt
▸until [[ condition ]]; do ...; done

Functions
▸my_func() { echo "$1 $2"; return 0; }
▸my_func arg1 arg2
▸$1, $2, ... — positional args inside function/script; $@ all args; $# arg count; $0 script name
Input/Output & Redirection
▸cmd > file — stdout to file (overwrite)
▸cmd >> file — stdout append
▸cmd 2> file — stderr to file

Troubleshooting Workflow (typical order)
1. ip a — confirm the interface has an IP
2. ip route — confirm a default route exists
3. ping <gateway> — confirm link to gateway works
4. ping 8.8.8.8 — confirm internet reachability (bypasses DNS)
5. dig google.com — confirm DNS resolution works
6. curl -v <url> / traceroute — narrow down where in the path it's failing
7. ss -tulpn / sudo lsof -i — confirm the local service is actually listening if it's a "can't connect to my own service" issue

Creating a Custom Service (Unit File)
Path: /etc/systemd/system/myapp.service
    [Unit]
    Description=My App
    After=network.target

    [Service]
    Type=simple
    User=myuser
    WorkingDirectory=/opt/myapp
    ExecStart=/usr/bin/python3 /opt/myapp/main.py
    Restart=on-failure
    RestartSec=5

    [Install]
    WantedBy=multi-user.target
Then:
▸sudo systemctl daemon-reload
▸sudo systemctl enable --now myapp
▸journalctl -u myapp -f — watch it come up
Common Type= values: simple (default, long-running foreground process), oneshot (runs and exits), forking (daemonizes itself), notify (signals readiness via sd_notify)
Timers (cron alternative, integrates with systemd/journalctl)
Path: /etc/systemd/system/myapp.timer
    [Unit]
    Description=Run myapp daily

    [Timer]
    OnCalendar=daily
    Persistent=true

    [Install]
    WantedBy=timers.target
▸Pair with a matching myapp.service (Type=oneshot) that does the actual work
▸sudo systemctl enable --now myapp.timer
▸systemctl list-timers — see all timers and next run time
▸See cron_cheatsheet.txt for the traditional crontab approach — timers are generally preferred on systemd systems for better logging/dependency handling

ENTRY 06

cron

Crontab Field Syntax
    * * * * * command
    │ │ │ │ │
    │ │ │ │ └── day of week (0-7, both 0 and 7 = Sunday)
    │ │ │ └──── month (1-12)
    │ │ └────── day of month (1-31)
    │ └──────── hour (0-23)
    └────────── minute (0-59)
▸Comma: 1,15 — specific values
▸Dash: 1-5 — range
▸Slash: */15 — every N (e.g. */15 in minute field = every 15 min)
▸Combine: 0 9-17/2 * * 1-5 — on the hour, every 2 hours from 9-17, weekdays only
Managing Your Crontab
▸crontab -e — edit your own crontab (opens in $EDITOR)
▸crontab -l — list your current crontab
▸crontab -r — remove your entire crontab (careful — no confirmation, and no undo)
▸sudo crontab -u <user> -e — edit another user's crontab
▸sudo crontab -u <user> -l
Special Strings (shortcuts for common schedules)
▸@reboot — run once at startup
▸@yearly / @annually — 0 0 1 1 *
▸@monthly — 0 0 1 * *
▸@weekly — 0 0 * * 0
▸@daily / @midnight — 0 0 * * *
▸@hourly — 0 * * * *
Examples
▸0 3 * * * /home/user/backup.sh — run backup.sh daily at 3:00 AM
▸*/5 * * * * /usr/bin/python3 /opt/check.py — every 5 minutes
▸0 0 * * 0 /home/user/weekly_report.sh — every Sunday at midnight
▸30 2 1 * * /home/user/monthly_cleanup.sh — 2:30 AM on the 1st of every month
▸@reboot /home/user/start_service.sh — run once when the system boots
System-Wide Cron Locations (no crontab -e needed)
▸/etc/crontab — system crontab, has an extra "user" field before the command
▸/etc/cron.d/ — drop-in files, same format as /etc/crontab (used by packages)
▸/etc/cron.daily/ , cron.hourly/ , cron.weekly/ , cron.monthly/ — just drop an executable script here, no cron syntax needed, run via run-parts
Logging & Debugging
▸Cron jobs run with a minimal environment — no full $PATH, no interactive shell config loaded. Always use absolute paths in scripts/commands.
▸Redirect output so you can debug failures: 0 3 * * * /home/user/backup.sh >> /home/user/backup.log 2>&1
▸grep CRON /var/log/syslog — see cron's own execution log (Debian/Ubuntu)
▸journalctl -u cron -f — same, via systemd journal on distros where cron logs there
▸MAILTO="" at the top of a crontab disables cron's default behavior of emailing job output to the user (set to an address instead if you want the emails)
Environment Gotchas
▸Cron doesn't source ~/.bashrc or ~/.profile — if a script relies on env vars, source them explicitly inside the script or set them at the top of the crontab: PATH=/usr/local/bin:/usr/bin:/bin
▸Test scripts with `env -i /bin/bash -c "script.sh"` to simulate cron's minimal environment
▸For scripts needing a specific working directory, `cd` explicitly inside the script rather than assuming cron starts there — cron typically starts in the user's home directory
Cron vs systemd Timers
▸Cron: simpler syntax, universally available, minimal logging by default
▸systemd timers: better logging via journalctl, can express dependencies (e.g. wait for network), handle missed runs on a system that was off (Persistent=true) — see systemd_cheatsheet.txt
▸Either is fine for simple scheduled jobs; timers are worth the extra setup for anything where you need reliable logging or missed-run recovery

SSH / SFTP / rsync

SSH Basics
▸ssh <user>@<host>
▸ssh <user>@<host> -p <port>
▸ssh <user>@<host> "command" — run a single remote command and exit
▸ssh -i <keyfile> <user>@<host> — use a specific private key
▸exit / Ctrl+D — close the session
SSH Keys
▸ssh-keygen -t ed25519 -C "comment" — generate a modern key pair (preferred over RSA now)
▸ssh-keygen -t rsa -b 4096 -C "comment" — if ed25519 isn't supported by the target (rare/legacy systems)
▸ssh-copy-id -i <keyfile>.pub <user>@<host> — install your public key on a remote host's authorized_keys
▸Manual alternative: cat ~/.ssh/id_ed25519.pub | ssh <user>@<host> "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys"
▸chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys — required permissions or SSH will reject the key
SSH Agent (avoid re-typing your key passphrase)
▸eval "$(ssh-agent -s)"
▸ssh-add ~/.ssh/id_ed25519
▸ssh-add -l — list loaded keys
▸ssh-add -D — remove all keys from agent
SSH Config File (~/.ssh/config)
    Host myvps
        HostName 203.0.113.10
        User myuser
        Port 22
        IdentityFile ~/.ssh/id_ed25519

    Then just: ssh myvps
▸Handy directives: ForwardAgent yes, ServerAliveInterval 60, StrictHostKeyChecking accept-new
Port Forwarding / Tunneling
▸ssh -L <local_port>:<dest_host>:<dest_port> <user>@<jump_host> — local forward (access a remote-only service on localhost)
▸ssh -R <remote_port>:<local_host>:<local_port> <user>@<host> — remote forward (expose local service to the remote side)
▸ssh -D <port> <user>@<host> — dynamic SOCKS proxy (route browser traffic through the SSH host)
▸ssh -N -f ... — don't execute a remote command, just hold the forward, run in background
▸ssh -J <jumphost> <user>@<target> — jump host / bastion hop in one command
SFTP
▸sftp <user>@<host>
▸sftp -i <keyfile> -P <port> <user>@<host>
Within an sftp session:
▸ls / lls — remote / local listing
▸cd / lcd — remote / local change dir
▸get <file> — download
▸get -r <dir> — download recursively
▸put <file> — upload
▸put -r <dir> — upload recursively
▸pwd / lpwd
▸exit
SCP (simple copy, being superseded by rsync/sftp but still common)
▸scp <file> <user>@<host>:<remote_path> — upload
▸scp <user>@<host>:<remote_path> <local_path> — download
▸scp -r <dir> <user>@<host>:<remote_path> — recursive
▸scp -P <port> ... — note: capital -P for scp, lowercase -p for ssh/sftp
Rsync
▸rsync -avz <src> <user>@<host>:<dest> — archive mode, verbose, compressed — the standard combo
▸rsync -avz -e "ssh -p <port>" <src> <dest> — custom SSH port
▸rsync -avz --delete <src> <dest> — mirror exactly, deleting files at dest not present in src (careful — destructive)
▸rsync -avzn <src> <dest> — dry run, add -n to preview what would happen
▸rsync -avz --progress <src> <dest> — show per-file progress
▸rsync -avz --exclude='.git' --exclude='node_modules' <src> <dest>
▸Trailing slash on source matters: `dir/` copies dir's contents into dest; `dir` (no slash) copies dir itself into dest
▸rsync over SSH is the standard way to do incremental backups — only changed blocks transfer after the first sync
Hardening an SSH Server (/etc/ssh/sshd_config)
▸PermitRootLogin no (or prohibit-password if you must allow root with keys only)
▸PasswordAuthentication no — key-only auth
▸Port <non-default> — mild obscurity, not real security by itself
▸AllowUsers <user1> <user2> — restrict to specific accounts
▸Restart after changes: sudo systemctl restart sshd
▸Test config before restarting: sudo sshd -t
▸Consider fail2ban to auto-block repeated failed login attempts
Troubleshooting
▸ssh -v / -vv / -vvv <host> — verbose connection debugging, increasing detail
▸ssh-keygen -R <host> — remove a stale host key from known_hosts (after host reinstall/IP reuse)
▸Permission denied (publickey) usually means: wrong key, key not in authorized_keys, or wrong permissions on ~/.ssh

Initial VPS Setup (do this immediately after provisioning)
1. SSH in with the root password emailed at signup:
   ssh root@<your-vps-ip>
2. Add your SSH public key and disable password auth:
   - Add key: mkdir -p ~/.ssh && echo "<pubkey>" >> ~/.ssh/authorized_keys && chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys
   - Edit /etc/ssh/sshd_config: PasswordAuthentication no, PermitRootLogin prohibit-password (or no, once you have a sudo user)
   - sudo systemctl restart sshd
3. Create a non-root sudo user (don't operate as root day-to-day):
   adduser <name> && usermod -aG sudo <name>
4. Update the system: sudo apt update && sudo apt full-upgrade -y (Ubuntu/Debian) or dnf upgrade (AlmaLinux/Rocky)
5. Set the hostname: sudo hostnamectl set-hostname <name>
6. Set up a firewall (ufw allow OpenSSH first so you don't lock yourself out, then ufw enable)
7. Set the timezone: sudo timedatectl set-timezone <Region/City>
8. Consider fail2ban for SSH brute-force protection: sudo apt install fail2ban
Rescue Mode / Recovery
▸If the server won't boot: Control Panel > Server > Actions > Rescue System — boots a minimal Linux environment so you can chroot in and fix configs, reset a lost password, or recover data
▸After a reboot into rescue, mount the real root partition (often /dev/sda1 or /dev/vda1) and chroot before running fixes
Reinstalling the OS
▸Control Panel > Server > Reinstall — wipes the disk and lets you pick a new OS image (this is destructive; snapshot/back up first if you need existing data)
▸Custom images can be uploaded and deployed via the DevOps tools section for repeatable setups
Snapshots & Backups
▸Snapshots are point-in-time, manually triggered, usually a few free slots depending on plan — good before risky changes
▸Backups (if purchased as add-on) run on a schedule and are separate from snapshots — check retention window in the panel
▸Snapshots/backups live on Contabo's infrastructure, not a substitute for off-site backups of critical data (consider rsync/restic to another location too)
Networking
▸Additional IPs, reverse DNS (PTR records), and private networking (if applicable to your plan) are configured from the panel's network section
▸Default firewall is OS-level (ufw/iptables/nftables) — Contabo doesn't provide a cloud firewall layer the way some providers do, so harden the OS firewall yourself
Monitoring Resource Usage
▸htop / top — live CPU/mem usage
▸vnstat — bandwidth usage over time (install with apt, useful since Contabo plans have traffic limits)
▸df -h && free -h — quick disk/memory check

Claude Code — Best Practices

1. Decide the basics before opening Claude
Have rough answers to these — Claude can help you decide, but knowing your own constraints
first speeds things up a lot:
▸Stack: static site generator (Astro, Hugo, Next.js, 11ty) vs. full framework vs. plain
HTML/CSS? For a tech blog, a static site generator is usually the right call — fast, simple
hosting, good for markdown content.
▸Hosting: Vercel/Netlify/GitHub Pages/self-hosted? This affects some setup choices.
▸Content workflow: Markdown files in the repo, or a CMS?
If you're not sure, that's fine — just tell Claude your general goal and let it propose
options rather than defaulting silently.
2. Set up the folder and git
mkdir tech-blog && cd tech-blog
git init
Do this yourself first (or ask Claude to). A git repo from the start means every change is
reversible and diffable — important once Claude starts making edits.
3. Open Claude Code and scaffold
claude
Then describe the goal in plain language: "I want to build a tech blog. I'm thinking
[Astro/Next/etc], markdown posts, deployed to [Vercel/etc]. Help me scaffold this."
For a project starting from nothing, it's often worth having Claude interview you first:
ask it to use AskUserQuestion to nail down things like styling approach (Tailwind? plain
CSS?), whether you want dark mode, RSS feed, tags/categories, comments, search, etc. This
front-loads decisions instead of Claude guessing and you correcting later.
4. Let it scaffold, then run /init
Once there's actual code/structure in the folder (even just a starter template),
run /init to generate CLAUDE.md. Doing it after scaffolding (not before, on an empty folder)
means it captures real conventions — file structure, commands like npm run dev, naming
patterns — instead of nothing.
Then hand-add a few things /init can't infer:
▸Your writing voice/tone preferences for post content, if Claude will help draft posts
▸Any hard rules (e.g., "always run npm run build before considering a change done")
▸Deployment specifics
5. Use plan mode for the first big structural pass
For the initial architecture (routing, layout, content collections config), toggle
plan mode (Shift+Tab) so Claude proposes an approach before writing files — cheap way
to catch a wrong direction (e.g., wrong framework idiom) before it's
baked into a dozen files.
6. Iterate in small loops after that
Once the skeleton exists, day-to-day work (new posts, components, styling tweaks) doesn't
need plan mode — just describe the change and let it run, checking the dev server (/run
or just asking it to start the dev server) as you go.
7. Commit as you go
Ask Claude to commit at natural checkpoints (scaffold done, first post live, styling
pass done) rather than one giant commit — easier to roll back a bad iteration.
TL;DR order of operations: decide stack/hosting → git init → describe goal, let
Claude interview you if scope is fuzzy → scaffold → /init → hand-edit CLAUDE.md
with a few extras → plan mode for architecture → normal mode for iteration → commit
along the way.-
